# 数据管理平台 · 三核心模块业务定位

> 本文档回答框架第三章的核心三问：「解决什么问题 / 不做什么 / 去掉会怎样」。
> 目的是把三个核心模块从「功能清单」升维成「业务建模」。
> 配套文档：《数据管理平台核心模块梳理.md》（功能视角）、《数据管理平台-核心业务主流程.md》（流程视角）。

---

## 一、数据管理模块（theme-management）

### ① 解决什么问题

解决「平台要管哪几类业务数据」的问题。它建立「一级主题」这个**分类骨架**，把公司的业务数据划分成主题域（客户、交易…），并给每个主题挂上报送属性（是否监管、报给谁、什么类型、谁负责）。

**一句话：它是整个平台的「目录 / 分类体系」，给数据开发提供组织维度。**

### ② 不做什么

- 不管理具体数据块的口径（那是数据开发模块的活）
- 不驱动检视 / 投产流程（那是项目管理模块的活）
- 不做实际数据开发（写 SQL / ETL 在别的平台）

### ③ 如果去掉会怎样

- 所有数据块失去归属，变成一堆散乱的口径，无法按主题组织
- 「是否监管、报给谁」等报送属性无处维护，**监管报送的合规性会失控**
- 主题 → 数据块的联动筛选失效，数据开发模块失去上游分类维度

## 二、数据开发模块（data-dev-spec）

### ① 解决什么问题

解决「每块数据怎么定义、怎么实现、怎么流转」的问题。它维护两类核心资产：**业务口径**（业务上这个数怎么定义）和**技术口径**（技术上怎么实现），并驱动口径走完「澄清 → 开发 → 检视 → 验收 → 投产」全生命周期。

**一句话：它是平台的「核心生产能力」，产出的是「口径」这个核心资产。**

### ② 不做什么

- 不写 SQL / ETL（实际开发在别的平台）
- 不做主题分类（那是数据管理模块的活）
- 不做批量交付 / 批次组织（那是项目管理模块的活）
- 不负责最终产物（报文 / 报表 / 数据块的最终形态在别的平台）

### ③ 如果去掉会怎样

- 口径无处登记、无版本、无对比、**变更无法追溯**
- 检视 / 投产流程失去对象（检视的就是口径本身，口径没了流程无从谈起）
- 整个平台失去存在意义——「口径变更可追溯、可审计、可控制」正是平台的核心使命，而这个模块是它的落地点（版本 + 变更日志 + 流程状态）

## 三、项目管理模块（projects-management）

### ① 解决什么问题

解决「怎么把散的口径变更组织成一次可交付的批次」的问题。它以「项目」为单位，把多个数据块口径 + 质量规则打包关联，实现**批量检视、批量投产**。

**一句话：它是平台的「交付与检视组织层」，把口径的「生产」变成「交付」。**

### ② 不做什么

- 不做口径的登记和维护（那是数据开发模块的活）
- 不做主题分类（数据管理模块的活）
- 不写 SQL / ETL（别的平台）
- 立项申请：
  - **现状特例**：立项在公司统一项目申请平台，本平台只登记立项结果（公司组织流程导致）
  - **理想设计**：平台内直接「项目申请 → 立项 → 走流程」，形成闭环

### ③ 如果去掉会怎样

- 口径变更变成零散个体，无法按批次管理、批量检视、批量投产
- 检视 / 投产失去「项目」这个组织载体，每个数据块都要单独走流程，效率失控
- 无法满足「一次投产一批相关口径」的业务诉求（监管报送往往是一次投产一批）
