## 一、核心问题陈述

在没有这个平台之前，口径变更靠邮件、文档、口口相传管理，导致三个核心痛点：

1. **口径变更无法追溯** —— 谁改的、为什么改、什么时候改，都查不到；
2. **出数错误频发且难追责** —— 上下游口径不一致，出了错也定不了责；
3. **检视投产流程不可控** —— 靠线下催，进度不透明，风险不可控。

**本平台的核心使命：让每一次口径变更可追溯、可审计、可控制，保障下游数据可信。**

### 三句话价值主张（对应框架第五章）

1. **一句话定位**：企业级数据口径变更的全生命周期管理平台。
2. **核心价值**：让每一次口径变更可追溯、可审计、可控制，保障下游数据可信。
3. **如果不存在的后果**：口径变更混乱，上下游数据不一致，数据事故频发且无法定责。

## 二、体系位置

```
                    ┌──────────────────────────────┐
                    │ 业务方 + 公司统一项目申请平台   │
                    │  （提需求 / 立项）              │
                    └──────────────┬───────────────┘
                                   │ 立项结果
                                   ▼
        ┌────────────────────────────────────────────┐
        │          数据管理平台（你的系统）            │
        │   主题分类 / 口径管理 / 检视投产流程          │
        └──────────┬────────────────────┬────────────┘
                   │ 口径引用            │ 上线状态
                   ▼                    ▼
        ┌──────────────────┐   ┌──────────────────┐
        │ 代码开发平台      │   │ 上线平台          │
        │ (写 SQL / ETL)   │   │ (投产 / 发布)    │
        └──────────────────┘   └──────────────────┘
```

- **上游**：业务方（提需求）+ 公司统一项目申请平台（立项）
- **本平台**：主题分类、口径管理、检视投产流程编排
- **下游**：代码开发平台（写 SQL/ETL）、上线平台（投产/发布）、监管报送系统（报文/报表最终去向）、下游数据消费方

## 三、用户角色

| 角色 | 用平台做什么 | 最关心什么 | 频率 |
| --- | --- | --- | --- |
| 业务方 | 提需求（多在平台外） | 需求能落地 | 低频 |
| 业务人员 | 登记业务口径 | 口径说清楚、少返工 | 中频 |
| 开发负责人 | 申请项目 + 本平台创建项目 | 立项顺利 | 低频 |
| 开发人员 | 澄清 + 填技术口径 + 写代码 | 需求清晰、口径明确 | 高频 |
| 项目负责人（检视人） | 口径检视 + 代码检视 + 验收 | 风险可控、需求合理 | 中频 |
| 测试人员 | 验收阶段测试 | 测试通过 | 中频 |
