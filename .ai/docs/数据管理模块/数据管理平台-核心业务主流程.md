# 数据管理平台 · 核心业务主流程

> 本文档记录数据管理平台（数据开发管理平台）的完整业务主流程：从项目立项到口径投产的全生命周期。
> 核心机制是「业务口径线(status)」与「技术口径线(devStatus)」两条并行状态机。
> 配套文档：《数据管理平台核心模块梳理.md》（功能与代码视角）、《数据管理平台-业务梳理框架.md》（分析框架）。

---

## 一、平台定位（一句话）

**本平台是数据开发的「编排层」**：管理口径规格与检视投产流程，真正的代码开发和上线在别的平台执行。

```
上游：公司统一项目申请平台（立项）
        ↓
本平台：口径规格管理 + 检视投产流程编排
        ↓
下游：代码开发平台（写代码）、上线平台（投产）
```

---

## 二、完整主流程图

```
【平台外】公司统一项目申请平台
  业务方提需求 → 开发负责人申请项目 → 立项成功
                        │
                        ▼
① 项目登记【本平台 · 项目管理】开发负责人手动创建项目
                        │
                        ▼
② 业务口径登记【本平台 · 数据开发】业务人员对目标主题/数据块的口径、要素增删改
                        │
                        ▼
③ 澄清【status 10→20】开发 ⇄ 业务 逐条过改动点，确认本次开发什么
                        │
                        ▼
④ 口径检视【devStatus 10→20】项目负责人审口径：信息同步是否完成 + 需求是否合理
                        │
                        ▼
⑤ 开发【status →50】①本平台填技术口径(表/技术/要素代码) ②别处写代码 ③回填本平台
                        │  → devStatus 30「代码可检视」
                        ▼
⑥ 代码检视【devStatus 30→40】项目负责人跨平台审代码是否合理
                        │
                        ▼
⑦ 验收【status →60】项目负责人在其他平台看效果 + 测试人员测试通过
                        │
                        ▼
⑧ 投产【status →70】本平台标记"已投产"，实际上线在别的平台触发（专门上线流程）
```

## 三、两条状态线

### 3.1 业务口径线（status）

| 状态码 | 名称 | 语义 |
| --- | --- | --- |
| 10 | 待检视 | 数据块创建后的初始状态 |
| 20 | 澄清完成 | 开发 ⇄ 业务已逐条对齐改动点 |
| 50 | 开发完成 | 技术口径已填 + 代码已开发并回填 |
| 60 | 验收 | 其他平台看到效果 + 测试通过 |
| 70 | 投产 | 本平台标记已投产，实际上线在别处 |

> 注：30（取数）/ 40（验证）状态在代码中保留但已精简，当前主流程为「澄清 → 开发 → 验收 → 投产」。

### 3.2 技术口径线（devStatus）

| 状态码 | 名称 | 语义 |
| --- | --- | --- |
| 00/空 | 初始 | 尚未开始 |
| 10 | 口径可检视 | 澄清已完成，可以审口径了 |
| 20 | 技术口径验收通过 | 项目负责人完成信息同步 + 需求合理性已把关 |
| 30 | 代码可检视 | ①别处代码已开发完成 ②表/技术/备注/要素代码已回填本平台 |
| 40 | 代码验收通过 | 代码检视通过 |

### 3.3 交织关系

| 阶段 | 业务口径线 status | 技术口径线 devStatus | 说明 |
| --- | --- | --- | --- |
| 初始 | 10 | 00 | 数据块创建后 |
| 澄清 | 10 → 20 | 00 → 10 | 开发⇄业务确认需求 |
| 口径检视 | — | 10 → 20 | 项目负责人审口径 |
| 开发 | 20 → 50 | 20 → 30 | 填技术口径 + 写代码 + 回填 |
| 代码检视 | — | 30 → 40 | 项目负责人跨平台审代码 |
| 验收 | 50 → 60 | — | 别处看效果 + 测试通过 |
| 投产 | 60 → 70 | — | 别处触发上线 |

## 四、分阶段详解

| 阶段 | 参与者 | 做什么 | 状态变化 | 发生地 |
| --- | --- | --- | --- | --- |
| ① 立项 | 业务方、开发负责人 | 提需求、申请项目 | — | 平台外 |
| ② 项目登记 | 开发负责人 | 手动创建项目，登记立项结果 | projectState=10 | 本平台 |
| ③ 业务口径登记 | 业务人员 | 对主题/数据块的口径、要素增删改 | — | 本平台 |
| ④ 澄清 | 开发人员、业务人员 | 逐条过改动点，避免理解有误 | status 10→20，devStatus 00→10 | 本平台 |
| ⑤ 口径检视 | 项目负责人（检视人） | 审口径：信息同步是否完成、需求是否合理 | devStatus 10→20 | 本平台 |
| ⑥ 开发 | 开发人员 | 填技术口径 + 别处写代码 + 回填本平台 | status 20→50，devStatus 20→30 | 本平台 + 代码平台 |
| ⑦ 代码检视 | 项目负责人（检视人） | 跨平台审代码是否合理 | devStatus 30→40 | 跨平台 |
| ⑧ 验收 | 项目负责人、测试人员 | 别处看效果 + 测试通过 | status 50→60 | 跨平台 |
| ⑨ 投产 | 上线流程 | 本平台标记，别处触发上线 | status 60→70 | 本平台 + 上线平台 |

## 五、角色分工

| 角色 | 负责环节 | 说明 |
| --- | --- | --- |
| 业务方 | 提需求 | 提出要做什么（平台外） |
| 开发负责人 | 申请项目 + 本平台创建项目 | 立项与登记 |
| 业务人员 | 登记业务口径 | 对主题/数据块的口径、要素增删改 |
| 开发人员 | 澄清 + 填技术口径 + 写代码 + 回填 | 技术实现 |
| 项目负责人（检视人） | 口径检视 + 代码检视 + 验收 | 跨平台综合判断 |
| 测试人员 | 验收阶段测试 | 测试通过是验收前提 |
| 上线流程 | 投产 | 专门的上线流程（别的平台） |

## 六、关键洞察（从本次梳理中提炼）

1. **平台是编排层，不是执行层**：代码开发在别的平台、上线在别的平台，本平台管的是口径规格 + 流程状态。
2. **「可检视」= 准备就绪，而非「正在检视」**：devStatus 的「可检视」表示前置工作已完成、可以被审查。
3. **检视/验收是跨平台综合判断**：项目负责人要两头看——本平台看口径，别的平台看代码和运行效果。
4. **两条状态线各管一摊**：业务线(status)管「业务走到哪一步」，技术线(devStatus)管「技术准备到哪一步」。

## 七、横切机制：版本与批次

主流程是「时间维度」（一个数据块从生到死），但平台还叠了两个横切维度，三者叠加才是完整业务模型：

```
流程维度（status / devStatus）：一个数据块从待检视 → 投产
版本维度（version）：          每次变更留痕，可纵向对比
批次维度（project）：          多个数据块打包，批量检视投产
```

### 7.1 版本维度（变更留痕）

| 概念 | 含义 | 对应实现 |
| --- | --- | --- |
| 业务口径版本 | 每次业务口径变更提交产生新版本，需填变更说明 + 自动生成变更日志 | `createDataBlockSpec` / `submitDataBlockSpec` |
| 技术口径版本 | 技术口径独立记版本，可「复制上个版本」再改 | `DataDevSpecIt` 编辑模式 |
| **版本对比**（纵向） | 同一数据块 v1 vs v2 的差异，回答「这次改了什么」 | `SpecCompareDrawer` |
| **口径对比**（横向） | 两个不同数据块之间的口径差异，回答「它们差在哪」 | `DataBlockSpecCompareDrawer` |

### 7.2 批次维度（项目打包交付）

- 「项目」= 一次交付批次，通过 `UploadAndProcessRecord` 将多个数据块口径打包关联（N:N）。
- 关联后可**批量检视、批量投产**，实现跨数据块的统一交付。
- 项目口径列表复用数据开发的版本对比 / 口径对比组件，保持口径口径一致。
