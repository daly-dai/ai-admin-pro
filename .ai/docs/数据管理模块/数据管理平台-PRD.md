# 数据管理平台 · 产品需求文档（PRD）

> 本文档由「业务梳理」过程中已确认的内容综合而成，作为平台的统一需求基线。
> 配套文档：模块梳理、主流程、三问、平台定位、数据模型、通用 vs 特例（同目录）。

---

## 一、问题陈述

业务方频繁变更数据口径，过去靠邮件、文档、口口相传管理，导致三个核心痛点：

1. **口径变更无法追溯** —— 谁改的、为什么改、什么时候改，都查不到；
2. **出数错误频发且难追责** —— 上下游口径不一致，出了错也定不了责；
3. **检视投产流程不可控** —— 靠线下催，进度不透明，风险不可控。

---

## 二、解决方案

建设一个**企业级数据口径管理平台**，定位为「编排层」——管理口径规格与检视投产流程，真正的代码开发和上线在别的平台执行。

- 以「一级主题」为分类骨架；
- 管理「业务口径 + 技术口径」的全生命周期（含版本）；
- 通过「项目」批次驱动检视与投产流程。

**使命**：让每一次口径变更可追溯、可审计、可控制，保障下游数据可信。

**体系位置**：

```
上游：业务方（提需求）+ 公司统一项目申请平台（立项）
  ↓
本平台：主题分类 / 口径管理 / 检视投产流程编排
  ↓
下游：代码开发平台（写 SQL/ETL）、上线平台（投产）、监管报送系统、下游数据消费方
```

## 三、用户故事

1. 作为**业务方**，我想提出数据口径变更需求，以便业务目标落地。
2. 作为**开发负责人**，我想在平台登记已立项的项目，以便组织后续开发与交付。
3. 作为**业务人员**，我想对主题下的数据块登记/修改业务口径（要素、口径增删改），以便明确数据的业务定义。
4. 作为**开发人员**，我想与业务人员逐条澄清改动点，以便避免理解偏差。
5. 作为**项目负责人（检视人）**，我想审口径（信息同步是否完成 + 需求是否合理），以便把好需求关。
6. 作为**开发人员**，我想填写技术口径（表、任务、要素技术口径）并在代码平台完成开发，以便落地实现。
7. 作为**项目负责人**，我想跨平台审代码是否合理，以便代码验收。
8. 作为**项目负责人 / 测试人员**，我想在其他平台看到运行效果并完成测试，以便验收。
9. 作为**上线流程**，我想在别的平台触发上线，以便口径投产。
10. 作为**业务人员 / 开发人员**，我想对比口径的版本差异，以便了解变更内容。
11. 作为**项目负责人**，我想把多个数据块口径关联进项目，以便批量检视、批量投产。

## 四、实施决策

### 4.1 模块划分（三个核心模块 + 边界）

| 模块 | 定位 | 一句话 |
| --- | --- | --- |
| 数据管理模块 | 以「一级主题」为维度，管理业务主题及报送属性 | 定「有哪些数据主题」（分类骨架） |
| 数据开发模块 | 以「数据块/报文/报表」为维度，管理业务口径与技术口径全生命周期 | 定「每块数据长什么样」（核心生产能力） |
| 项目管理模块 | 以「项目」为维度，关联口径与规则，驱动检视与投产流程 | 定「怎么批量交付」（交付组织层） |

### 4.2 两条并行状态机（决策核心）

**业务口径线（status）**：

```
10 待检视 → 20 澄清完成 → 50 开发完成 → 60 验收 → 70 投产
```

**技术口径线（devStatus）**：

```
00 初始 → 10 口径可检视 → 20 技术口径验收通过 → 30 代码可检视 → 40 代码验收通过
```

关键语义：**「可检视」= 准备就绪（前置工作已完成），而非「正在检视」**。

两条线的交织关系：

| 阶段 | 业务口径线 | 技术口径线 | 说明 |
| --- | --- | --- | --- |
| 初始 | 10 | 00 | 数据块创建后 |
| 澄清 | 10→20 | 00→10 | 开发⇄业务确认需求 |
| 口径检视 | — | 10→20 | 项目负责人审口径 |
| 开发 | 20→50 | 20→30 | 填技术口径 + 写代码 + 回填 |
| 代码检视 | — | 30→40 | 项目负责人跨平台审代码 |
| 验收 | 50→60 | — | 别处看效果 + 测试通过 |
| 投产 | 60→70 | — | 别处触发上线 |

### 4.3 版本管理

- 业务口径版本与技术口径版本**各自独立**；
- 每次变更提交产生新版本，需填变更说明 + 自动生成变更日志；
- 支持版本对比（同一数据块纵向对比）与口径对比（不同数据块横向对比）。

### 4.4 项目关联口径（批次维度）

- 项目通过关联记录关联 `(dataBlockId, version)`，与数据块口径为 N:N；
- **口径是资产，项目是批次**：同一口径可独立存在，也可在不同时间被不同项目关联；
- 关联后支持批量检视、批量投产。

### 4.5 数据模型

```
主题 1:N 数据块
数据块 1:N 业务口径（含业务要素）
数据块 1:N 技术口径（含要素技术口径）
项目 N:M 数据块口径
项目 N:M 规则
```

### 4.6 编排层定位

代码开发在代码平台、上线在上线平台；本平台只管理口径规格与流程状态，通过技术口径中的「表 / 任务」引用外部实现。

## 五、测试决策

> 说明：本次梳理未深入讨论测试策略，以下为基于平台特性的方向性建议，待补充。

- **状态机流转**：验证两条状态线在各阶段的合法 / 非法流转（重点：可检视的语义边界）。
- **版本管理**：验证变更提交产生新版本、版本对比正确、变更日志自动生成。
- **项目关联**：验证口径关联 / 取消关联、批量检视 / 投产的权限控制。
- **权限**：验证不同角色（业务 / 技术 / 检视人）可见操作的正确性。

## 六、范围外（Out of Scope）

- 实际代码开发（写 SQL / ETL）——在代码开发平台；
- 上线 / 投产的实际执行——在上线平台；
- 最终产物（报文 / 报表 / 数据块的最终形态）——在别的平台 / 下游；
- 项目立项申请——现状在公司统一项目申请平台（理想设计应内置，见待确认问题）。

## 八、补充说明（Further Notes）

- **平台是编排层，不是执行层**：这是理解全部设计的前提。
- **抽象视角（通用 vs 公司特例）**：立项外置、一表通主题、取数/验证状态码遗留、沙盒环境适配等为公司特例，剥离后不影响平台通用骨架。
- **抽象版定义**：企业级数据口径管理平台——以主题为分类骨架，管理业务口径 + 技术口径全生命周期（含版本），通过项目批次驱动检视投产，使每一次口径变更可追溯、可审计、可控制。
