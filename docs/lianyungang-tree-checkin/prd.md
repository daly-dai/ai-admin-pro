# 连云港千年古树打卡 · 产品需求文档（PRD）· 平台借力版

> 版本：v0.2（平台借力策略版）｜配套文档：`points-screening.md`（点位初筛清单）

## Problem Statement

连云港旅游的核心吸引力是"看海"，存在三个结构性问题：**旺季景区拥挤、淡季没有内容、游客停留时间短**。与此同时，全市拥有 **718 株官方养护的古树名木**（2024 年数据），分布在花果山、云台山、东磊、孔望山、云龙涧等点位，是天然的故事载体和打卡节点，但"藏在深山无人识"。

另一层问题是**单干成本**：从零做一个独立 App/小程序，缺流量入口、缺政府背书、缺数据授权，很难起量。连云港市已有官方智慧旅游平台"**智游连云港**"（文旅总入口），江苏省已有"**水韵江苏·长江百景**"集章打卡先例——**与其另起炉灶，不如借平台落地**。

## Solution

做一个**古树集章打卡专题**：把 30~50 棵"年限够老、有观赏性"的古树连成多条线路，游客到树前扫码打卡，**集齐一条线路解锁一枚勋章**。产品定位是"看海之外的第二条动线"，为外地看海游客提供多留一天的理由，为年轻打卡人群提供可晒的收集目标。

**平台借力三原则（本版核心变化）**：

1. **技术借力**——地图与定位用**高德**（地图 SDK / 定位 SDK / POI / 自定义兴趣点），不自己画地图、不自己搞定位
2. **载体借力**——不开发独立 App；目标形态是**挂靠"智游连云港"的古树专题**（小程序/H5 入口），探索期先做 H5 演示版
3. **运营借力**——玩法对标省级"水韵江苏"集章先例，落地时以"给 718 株古树养护工作一个游客可见的出口"为合作叙事，争取文旅局背书

**必须自有的部分**（平台没有现成的，是产品灵魂）：古树数据档案、打卡判定逻辑、**勋章体系**、打卡统计后台。

## 平台借力策略（调研结论）

| 平台 | 现成能力 | 怎么借 | 不能借什么 |
|------|----------|--------|-----------|
| **高德地图** | C 端"足迹/点亮足迹/点亮城市"（用户自发记录足迹）；开放平台：地图 SDK、定位 SDK、POI 搜索、自定义兴趣点、轨迹服务 | 地图底图、点位标注、定位打卡的技术底座；引导用户在高德同步"点亮"形成联动 | **没有开放给第三方的打卡勋章 API**——勋章必须自建 |
| **智游连云港**（本市官方） | 连云港市文旅总入口/智慧旅游服务平台，2023 年上线，持续运营（近期上线宠物友好地图） | **首选落地方向**：古树打卡作为平台专题挂靠，借用户基数与政府背书 | 深度数据打通需商务谈判，探索期不可控 |
| **水韵江苏**（省级） | "水韵江苏·长江百景"集章打卡活动（2024-11 上线） | 玩法合规背书；未来可作为省级体系下的地市专题申报 | 专题申报流程未确认，探索期够不着 |
| **微信生态** | 小程序、扫一扫、公众号、分享链路 | 载体与传播层：扫码打卡、勋章分享卡片 | 无现成集章玩法，需自建 |
| **抖音** | 景点 POI 打卡贴纸/同城内容 | 传播层：鼓励用户打卡后发视频带 POI | 不是勋章平台，仅引流 |
| **科普易行·智慧地图**（数字盖章平台，2024 报道） | 现成的"数字盖章/打卡"技术平台 | 评估直接租用/接入的可能，省自研成本 | 运营主体与接入方式 `[TBD]` |

**决策**：探索期（阶段 0）= 自建 H5 演示版（技术借高德）+ 以合作提案形式接触智游连云港；合作期（阶段 1）= 专题挂靠智游连云港 + 微信小程序入口 + 二维码物料铺设。**勋章、数据、品牌始终自持**。

## User Stories

1. 作为**外地看海游客**，我想在地图上看到古树点位与线路，以便规划一条"看海之外"的动线
2. 作为**游客**，我想查看每棵古树的档案（树种、树龄、故事、交通、照片、最佳观赏期），以便打卡不只是签到
3. 作为**打卡者**，我想在树前扫码（或 GPS 兜底）打卡，以便收集这棵古树
4. 作为**打卡者**，我想看到收集进度与线路进度条，以便有持续目标感
5. 作为**打卡者**，我想集齐一条线路后解锁该线路勋章，以便获得成就感
6. 作为**打卡者**，我想集齐全部线路获得终极大勋章，以便有终极目标
7. 作为**年轻打卡人群**，我想把勋章/进度生成分享卡片，以便晒给朋友形成传播
8. 作为**智游连云港平台方**，我想平台有话题性文旅专题，以便提升平台活跃与本地内容供给
9. 作为**市文旅局**，我想让 718 株古树养护工作有游客可见的出口，以便古树保护被看见、被认可
10. 作为**管理员**，我想维护古树档案、线路、勋章配置与打卡统计，以便内容可控、运营可调

## Implementation Decisions

**MVP 范围（最小闭环）**：古树列表/地图 → 点位详情 → 扫码打卡 → 按线路集齐判定 → 勋章解锁 + 进度展示。线路为"归属 + 集齐判定"的轻量结构；分享卡片后置。

**总体架构**：
- 移动端：H5 原型（探索期）→ 挂靠智游连云港的专题 + 微信小程序（合作期）；地图/定位用高德 SDK/开放平台
- 管理后台：复用当前 aI-admin-pro 项目（React 18 + TS + @dalydb/sdesign + antd 5 + Zustand + Rsbuild），按 AGENTS.md 规约走 CRUD Lane
- 后端 API：新建，接口命名沿用 `{Entity}{动作}By{HTTP}`

**数据模型草案**（原型级，待后端确认）：

```
Tree（古树档案）: id / name / species / ageEstimate / story / photos /
                  lat / lng / address / lineId / qrToken / bestSeason / status
Line（线路）:     id / name / description / cover / sort
Badge（勋章）:    id / lineId / name / icon / description / condition
CheckIn（打卡）:  id / treeId / userId / method(qr|gps) / locationSnapshot / createdAt
User（用户）:     H5 阶段匿名设备号；合作期对接智游连云港/微信 openid
```

**打卡与防作弊**：二维码为主（每树独立 token，限次），GPS 兜底（高德定位 + 距离阈值 + 漂移容错）。原则：太严没人玩，太松勋章不值钱；MVP 先宽松后收紧。

**点位与观赏季**：初筛 11 个点位见 `points-screening.md`；双季卖点——春季（玉兰、糯米茶花开）+ 秋季（银杏黄金甲）。

**管理后台模块**：古树档案 CRUD、线路管理、勋章配置、打卡记录与统计。按 CRUD Lane 模板填空生成。

## Testing Decisions

- 管理后台：走 `pnpm verify`（tsc + eslint + prettier）闸门
- 核心逻辑单测：**勋章解锁判定**（集齐边界：重复打卡、中途加入、多线路）与**打卡防作弊判定**（距离阈值、token 限次）
- 移动端：真机端到端手测（重点：高德定位在山区/景区内的精度与漂移容错、iOS Safari 定位授权、弱网扫码）

## Out of Scope

- 自研地图引擎、原生 App（明确排除）
- 与智游连云港的深度数据打通、统一登录（合作谈判后）
- 线下实体盖章、文创售卖、支付（后期）
- 古树 AI 识别、AR 导览、多语言
- 分享卡片、排行榜（阶段 1 后）

## Further Notes

- **借力不等于失控**：高德借技术、微信借载体、智游连云港借流量与背书，但勋章体系、用户数据、古树档案是自有资产
- **合作叙事（谈智游连云港/文旅局时用）**：718 株古树养护是政府有投入的工作，打卡专题让这份投入被游客看见——平台获得话题内容，古树获得公众关注，产品获得入口与背书
- **冷启动**：靠年轻打卡人群传播（勋章可晒是核心钩子）；借高德"点亮足迹"用户习惯做联动引导
